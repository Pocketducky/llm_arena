# Архитектура системы оценки суммаризаций ЭМК

Краткий обзор конвейера. Подробный разбор с результатами — в [REPORT.md](REPORT.md).

## Идея
Каждая пара «исходная ЭМК → суммаризация» проходит цепочку: сначала дешёвые
детерминированные проверки, затем дорогой ансамбль LLM-судей, и только то, что
прошло фильтр. Итоговое решение выносит код, а не «мнение» одной модели.

## Этапы (блоки)

```
ЭМК + суммаризация
      │
      ▼
[1] Препроцессор            preprocessor.py   — сегментация на канонические разделы
      ▼
[2] Объективный слой        objective_layer.py — детерминированная сверка фактов
      │                                          (числа, полярность, причинность,
      │                                          интерпретация, сущности)
      ▼
[3] Pre-evaluation gate     gate.py           — отсев заведомо непригодных до судей
      ▼
[4] LLM-as-Judge (3 раунда) judge.py          — R1 независимая оценка A–E →
      │                                          R2 перекрёстная рецензия →
      │                                          R3 финальный арбитр (стоп-правило E1)
      ▼
[5] Агрегация               aggregator.py     — детерминированная итоговая категория
      ▼
[6/7] Аудит, дрейф, отчёт   audit.py, drift.py, report.py, run_pipeline.py
```

## Таксономия оценки A–E
- **A. Клиническая точность** — достоверность фактов, чисел, терминологии (нет галлюцинаций).
- **B. Полнота** — покрытие жалоб, анамнезов, лабораторных и инструментальных данных.
- **C. Релевантность** — нет лишнего; всё включённое клинически значимо.
- **D. Структура** — соответствие схеме, отсутствие дублей, читаемость.
- **E. Безопасность** — нет клинически опасных ошибок. **E1 — стоп-правило**: одна
  подтверждённая опасная ошибка → категория «Неприемлемо» независимо от остального.

Итоговых категорий три: «Готово к клиническому применению» / «Требует
редактирования» / «Неприемлемо».

## Роли и модели
Пайплайн обращается к моделям только через абстрактные роли; соответствие
«роль → модель» задаёт профиль в `config.py`.

| Роль | Назначение | Модель в профиле `npkc` |
|---|---|---|
| judge_1 | независимый судья | qwen3.5-122b-fp8 |
| judge_2 | независимый судья | qwen3.5-122b-fp8 |
| judge_3 | независимый судья | qwen3.6-27b-fp8 |
| aggregator | финальный арбитр (проверка E1) | qwen3.5-122b-fp8 |

Два сильных судьи + один поменьше дают архитектурное разнообразие (декорреляция
ошибок) и экономят ресурс; сильный арбитр — на безопасность (E1).

## Бэкенды LLM
Весь доступ к моделям изолирован в `llm_client.py` и выбирается через
`config.LLM_BACKEND`:
- **vllm** — продакшн НПКЦ (OpenAI-совместимый API, `/v1/chat/completions`);
- **ollama** — локальная разработка на лёгких моделях.

Смена бэкенда или профиля не требует изменений в коде препроцессора, судей или
агрегатора — только конфигурация (см. `.env.example`).
