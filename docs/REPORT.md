# Итоговый отчёт: система автоматической оценки суммаризаций ЭМК (пилот)

> Подробный разбор: как устроен и работает алгоритм, что сделано на данный
> момент, какие получены результаты и **почему они именно такие**. Технический
> справочник по модулям — в [README.md](README.md); журнал инженерных правок —
> в [HANDOFF.md](HANDOFF.md).

---

## 1. Резюме

Построена и отлажена модульная система оценки качества суммаризаций
электронных медицинских карт (ЭМК), выполненных языковыми моделями. Система
сочетает **детерминированный объективный слой** (rule-based проверка фактов) и
**ансамбль LLM-судей** (3 судьи × 3 раунда + детерминированный агрегатор со
стоп-правилом безопасности E1), с **pre-evaluation gate** для отсева
вырожденных сводок.

**Ключевые результаты пилота (модель qwen3:8b локально через Ollama):**

| Что проверяли | Результат |
|---|---|
| Детекция искажений объективным слоём (synthetic, 370 пар) | critical recall **65.7%**, benign FPR **10.0%** |
| Сквозной прод-конвейер на искажениях (synthetic, 37 пар) | critical reject **71.4%**, benign reject **0.0%** |
| Выбор лучшей сводки среди 17 кандидатов одного пациента | **эталон занял 1-е место**; gate 17/17 pass; 0 сбоев JSON |

**Главный вывод.** Инфраструктура (gate, объективный слой, надёжность вывода
судей, агрегация, ранжирование) работает корректно и стабильно. Предел
точности на пилоте задаёт **качество суждений модели 8B**: она шумна и
недетерминирована на тонких типах искажений. Это измеренное, конкретное
обоснование перехода на целевую конфигурацию (DeepSeek-R1 70B × 3 +
Qwen3-Next-80B), заложенную в дизайне исследования.

## 2. Как работает алгоритм — сквозной ход одной пары

На вход подаётся пара **(исходная ЭМК, суммаризация)**. Пара проходит
последовательность из 8 независимо тестируемых блоков (0–7).

```
ЭМК + суммаризация
   │
   ▼  Блок 0  config.py + ollama_client.py — роли судей → модели; HTTP-клиент Ollama
   ▼  Блок 1  preprocessor.py — сегментация на канонические разделы
   ▼  Блок 2  objective_layer.py — ДЕТЕРМИНИРОВАННАЯ сверка фактов
   ▼  Блок 3  gate.py — pre-evaluation gate (бинарный фильтр; экономит GPU)
   ▼  Блок 4  judge.py — LLM-as-Judge: R1 (3 судьи) → R2 (cross-review) → R3 (агрегатор)
   ▼  Блок 5  aggregator.py + report.py — детерминированная категория + Excel-отчёт
   ▼  Блоки 6-7  synthetic/correlation/audit/drift/run_pipeline — валидация, аудит, дрейф
   ▼
Итоговая категория: «Готово» / «Требует редактирования» / «Неприемлемо»
```

### 2.1. Блок 0 — конфигурация и инфраструктура
Код пайплайна никогда не обращается к именам моделей — только к абстрактным
**ролям** (`judge_1..3`, `aggregator`). Соответствие «роль → модель» задаётся
**профилем** в `config.py`: `pilot` (всё на qwen3:8b — текущий) и `target`
(3×DeepSeek-R1 70B + Qwen3-Next-80B — для GPU-инфраструктуры). Смена профиля
не требует правок в коде. `ollama_client.py` — HTTP-клиент с восстановлением
«грязного» JSON, повторными попытками и панелью судей `JudgePanel`.

### 2.2. Блок 1 — препроцессор
`preprocessor.py` сегментирует и ЭМК, и суммаризацию на канонические разделы
(жалобы, анамнез заболевания, анамнез жизни, лабораторные данные,
инструментальные исследования и т.д.) — это «заземление» для судьи блока B
(полнота) и проверки структуры (D1).

### 2.3. Блок 2 — объективный слой (ядро детерминированной части)
`objective_layer.compare_texts(text_a, text_b, panel)` сверяет два текста по
**пяти типам проверяемых фактов**, без «мнения LLM о тексте»:

1. **Числа + единицы** (`extract_numeric_facts`, rule-based regex). Находит
   `NumericMismatch` (тот же показатель, другое значение: «56 лет»→«46 лет») и
   `UnitMismatch` (то же число, другая единица: «40 минут»→«40 часов»).
   Сопоставление по «подписи» показателя — чтобы не путать гемоглобин с
   эритроцитами в одной лабораторной панели.
2. **Полярность утверждений** (`extract_polarity_facts`). Ловит инверсию
   отрицания («купирован»→«не купирован») и антонимические пары
   («включают»↔«исключают», «госпитализирован»↔«выписан»).
3. **Ложная причинность** (`compare_causality`). Ловит введённую в кандидат
   причинную связку («вследствие», «по причине»), которой нет в референсе —
   тип, к которому слепы остальные сигналы.
4. **Ложная интерпретация** (`compare_interpretations`). Ловит оценочное слово
   при числе, **противоречащее референсному диапазону** («снижено
   (150/90 мм рт. ст.)» — это гипертензия). Отделяет critical-ложь от benign
   корректной интерпретации по медицинской верности; диапазоны заданы только
   для однозначных по единице величин (АД, ЧСС, гемоглобин, креатинин, явный
   избыток ферментов), неоднозначные пропускаются.
5. **Семантические сущности** (`extract_semantic_entities`, через LLM). Шесть
   категорий: диагнозы, препараты, процедуры, отделения, симптомы, анамнез
   жизни. Сравнение `compare_entity_sets` даёт precision/recall/F1 и устойчиво
   к шуму извлечения LLM (см. раздел 5.1).

Результат — `ObjectiveComparisonReport` с `hard_findings()` (читаемый список
жёстких расхождений для судей) и `to_summary()` (JSON для аудита).

### 2.4. Блок 3 — pre-evaluation gate
`gate.py` отсекает сводки, по которым и так понятно, что они непригодны
(нет ни одного диагноза/препарата), не вызывая дорогих судей. **Калибровка
зависит от задачи (`scope`):**
- `scope=None` (общая сжимающая сводка vs полный исходник): блокируется только
  полное отсутствие клинически критической категории (диагнозы/препараты,
  recall == 0); низкое покрытие прочего — закономерная компрессия, её
  оценивают судьи (блок B);
- `scope="radiologist"` (целевая выжимка под адресата): сущности источника
  сужаются фильтром релевантности, действует обычный порог recall.

### 2.5. Блок 4 — LLM-as-Judge (3 раунда)
`judge.py`:
- **R1** — 3 судьи независимо оценивают по блокам таксономии A–E (отдельный
  промпт на блок, заземлённый находками блоков 1–3);
- **R2** — cross-peer-review: каждый судья пересматривает оценку, видя полные
  отчёты двух коллег;
- **R3** — агрегатор синтезирует вердикт; промпт обязывает первым шагом явно
  проверить **стоп-правило E1** (критическая галлюцинация → автоматический
  «Неприемлемо»).

Все раунды работают с `think=False` и толерантным мерджем R2 — критично для
надёжности JSON (см. раздел 3.2).

### 2.6. Блок 5 — детерминированная агрегация и отчёт
`aggregator.py` выносит **итоговую категорию кодом, а не доверяя самооценке
LLM**: первым делом проверяет E1 по всем шести отчётам судей; категория —
функция от баллов блоков A–D и решения gate. `report.py` формирует Excel.

### 2.7. Блоки 6–7 — валидация, аудит, дрейф, оркестрация
`synthetic.py` (регрессия на наборе управляемых искажений), `correlation.py`
(корреляция с экспертной разметкой — инфраструктура готова, ждёт данных),
`audit.py` (JSONL-лог), `drift.py` (мониторинг дрейфа), `run_pipeline.py`
(сквозной прогон корпуса).

### 2.8. Технические детали этапов 1–3: алгоритмы, библиотеки, основания оценки

Принцип: **этапы 1–2 почти полностью детерминированы (regex + стандартная
библиотека Python), без «чёрного ящика».** Тяжёлый ML появляется точечно
(LLM-извлечение сущностей) и на этапе судей.

**Этап 1. Сегментация (`preprocessor.py`).** Только stdlib `re` и `dataclasses`
— никаких spaCy/nltk.
- ЭМК (`segment_emr`): поточный построчный разбор. Строка нормализуется
  (`_normalize_line`: нижний регистр, снятие кавычек/двоеточий) и проверяется
  против словаря ~8 категорийных header-regex (`_EMR_HEADER_PATTERNS`). Узнанный
  заголовок открывает раздел, остальное — тело; под-заголовки осмотра («Сердце»)
  намеренно не в словаре → нет дробления. Все повторы категории по визитам
  объединяются (`text_for`).
- Резервный режим (`_segment_by_inline_labels`) для нарративных карт без
  построчных заголовков (синтетика): ищет встроенные метки «Метка: текст»;
  включается, если построчный метод распознал < 30 % текста.
- Суммаризация (`segment_summary`): заголовок распознаётся по ФОРМЕ (markdown
  `##`, `**жирный:**`, нумерованный пункт), категория — по ключевым словам
  внутри (`_SUMMARY_KEYWORD_RULES`). Выход — `DocumentStructure` +
  `schema_compliance` (проверка D1: 5 разделов в верном порядке через сравнение
  подпоследовательностей).

**Этап 2. Объективный слой (`objective_layer.py`).** Библиотеки: stdlib `re` +
`difflib.SequenceMatcher` (алгоритм Ratcliff–Obershelp) для нечёткого сравнения
строк. Тяжёлых NLP/ML-зависимостей в rule-based ядре нет — сознательно.
- Числа: общий regex `_UNIT_RE`, единицы сгруппированы по категориям
  (возраст/длительность/витальные/лаб/размер/доза). Каждому числу присваивается
  «подпись» — ближайшее название показателя слева, ограниченное пунктуацией
  (`_extract_label`), чтобы «гемоглобин 115» ≠ «эритроциты 115».
- Полярность: (1) отрицание у предиката (`_PREDICATE_RE`); (2) антонимичные
  корневые пары (`_ANTONYM_RE`: включают↔исключают, госпитализирован↔выписан).
  В правила захардкожены только клинически-общие инверсии — открытые подмены
  отданы LLM-слою, чтобы не подгонять recall под тестовый набор.
- Ложная интерпретация: `_reference_polarity` — консервативные референсные
  диапазоны (АД ≥140/90→high, ЧСС, гемоглобин, креатинин, кардиоферменты),
  флаг при противоречии оценки значению; неоднозначные по единице величины
  пропускаются (точность важнее полноты).
- Сущности (единственная ML-часть): `extract_semantic_entities` через LLM
  (`JudgePanel.ask_json`, `think=False`); сопоставление нечёткое через
  `SequenceMatcher` с порогом **0.85** (поглощает опечатки/словоформы, но не
  склеивает реальные подмены: кардиореанимация↔нейрореанимация ≈ 0.73).
- Выход — `ObjectiveComparisonReport.hard_findings()`: список подтверждённых
  расхождений, подаётся судьям как заземление.

**Этап 3. Gate (`gate.py`).** Rule-based: покрытие сущностей из отчёта этапа 2 +
`scope` (см. 2.4).

**На чём основана оценка LLM (этап 4).** У модели нет встроенного медицинского
свода правил; её суждение опирается на сумму четырёх источников, и только их
совокупность даёт оценку:
1. предобученные медицинские знания модели (базовый, наименее надёжный слой);
2. **явное определение критерия в промпте** — формулировки подкритериев вписаны
   дословно из `SUBCRITERIA_LABELS_RU`; E1 («ложная аллергия, подмена диагноза —
   СТОП-ПРАВИЛО») и граница «опасность (E1) vs неточность (A1/A2)» заданы текстом,
   модель лишь применяет определение;
3. **контекст адресата (`scope`)** в `_role_intro` — релевантность (C) и полнота
   (B) оцениваются относительно того, кому адресована сводка;
4. **заземление объективным слоем** — для блоков A/E модель получает готовый
   список машинно-найденных расхождений и обязана классифицировать каждое.

Степень заземлённости разная: E1 (опасность) сильно заземлён (объективный слой +
стоп-правило в коде + ансамбль 3 судей + перекрёстная рецензия). C1/C2
(нерелевантность, клиническая значимость) — самые субъективные: объективного
заземления у блока C нет, он опирается на суждение модели в рамках `scope`.
Поэтому это подкритерии-баллы, а не стоп-правило, и именно они сильнее всего
выигрывают от перехода на 70B и от экспертной валидации.

## 3. Что сделано на данный момент

### 3.1. Рефакторинг объективного слоя (фиксы A–F)
- **A. Нечёткое сопоставление сущностей** — точное/подстрока/подмножество
  токенов/посимвольная близость ≥0.85. Поглощает опечатки, словоформы,
  расшифровки аббревиатур; реальные подмены остаются различимыми.
- **B. Фильтр значимости** — мусорные/служебные фантомные сущности не флагаются.
- **C. Режим B сверки** — референс изменён с исходника на эталон (искажения
  внедрены относительно эталона; сверка сопоставимого объёма).
- **D. Детектор ложной причинности** (`compare_causality`).
- **E. Фильтр артефактов извлечения** — self-grounding (доверяем сущности,
  только если она есть в своём тексте), cross-text сверка, стем-сопоставление,
  игнор обрамляющих слов («определение/тест/общий»).
- **F. Детектор ложной интерпретации** (`compare_interpretations`,
  референсные диапазоны).

### 3.2. Надёжность вывода судей (фикс G)
Была частая проблема: на больших структурированных ответах (особенно полный
отчёт A–E в R2) qwen3:8b обрывал JSON, и валидация «всё-или-ничего» отвергала
ответ → 3 провальные попытки → откат. Исправлено в корне:
- **`think=False`** во всех раундах судей — скрытые `<think>`-рассуждения
  больше не съедают бюджет `num_predict`;
- **толерантный мердж R2** (`_merge_full_report`) — ответ модели накладывается
  на валидный отчёт R1; обрыв/пропуск поля больше не фатален, R2 **никогда не
  падает**;
- увеличен `num_predict` для R2/R3.

Результат: на полном ночном прогоне (17 сводок, 15 часов) — **0 сбоев JSON**.

### 3.3. Калибровка gate под общие суммаризации (фикс H)
gate со `scope=None` отклонял ЛЮБУЮ сжатую сводку (включая эталон), т.к.
описательные категории (отделения/симптомы) закономерно не покрыты на >50%.
Сделан scope-aware (см. 2.4): эталон → pass, вырожденная сводка → reject.

### 3.4. Расширение онтологии сущностей
К 4 категориям (диагнозы/препараты/процедуры/отделения) добавлены **симптомы**
и **анамнез жизни** — частые цели галлюцинаций/пропусков. Fix E сделал
расширение безопасным от шума.

### 3.5. Валидационный контур `synthetic.py`
Два режима на синтетическом stress-наборе (Сеченовский ун-т): A — детекция
(эталон vs искажение через объективный слой), B — сквозной прод-прогон через
полный конвейер судей. Легенда искажений `ROW_DISTORTIONS` — единый источник
правды.

### 3.5a. Reference-метрики `reference_metrics.py` (ROUGE-L, BERTScore)
Reference-based метрики из дизайна (Раздел 4.2), применяются ТОЛЬКО при наличии
эталона — на синтетике (эталон стр.1 vs кандидат), флаг `synthetic.py --ref-metrics`.
ROUGE-L — без зависимостей; BERTScore — опционально (`requirements-metrics.txt`,
torch+transformers). В продуктивном пути (исходник → суммаризация) эталона нет,
метрики там не используются. Замечание: обе метрики КОАРСНЫЕ для одиночных
искажений (точечная замена слабо двигает балл: critical ≈ 0.98, benign ≈ 0.96 по
ROUGE-L) — служат общим индикатором близости к эталону, тонкую детекцию даёт
объективный слой + судьи.

### 3.6. Сквозной тест пациента `eval_patient.py`
Прод-сценарий «дан исходник ЭМК и 17 сводок-кандидатов — выбери лучшую»:
каждая сводка проходит gate + 3-раундовых судей, затем ранжирование. Режимы
`--representative`, `--recompute-objective`, `--report-only`; чекпоинты с
возобновлением; защита от сна (`caffeinate`).

### 3.7. Уборка репозитория
Удалён мёртвый код (старый монолит `evaluator.py`, `test_setup.py` —
в git-истории), очищен мусор, усилён `.gitignore`, удалены неиспользуемые
импорты, обновлена документация. Все self-check'и зелёные, `run_pipeline
--dry-run` (E2E-проводка) проходит.

## 4. Результаты

### 4.1. Режим A — детекция искажений объективным слоём (370 пар, 10 пациентов)

| Тип искажения | Критичность | recall / FPR | до фиксов |
|---|---|---|---|
| подмена_сущности | critical | **86.7%** | 10% |
| антонимическая_инверсия | critical | 83.3% | 83% |
| искажение_числа | critical | 76.7% | 77% |
| пропуск_контента | critical | 63.3% | 0% |
| вставка_отрицания | critical | 63.3% | 63% |
| галлюцинация | critical | 60.0% | 0% |
| ложная_интерпретация | critical | 36.7% → **80%*** | 37% |
| ложная_причинность | critical | 30.0% | 10% |
| **ИТОГО critical recall** | | **65.7%** | 39.1% |
| **ИТОГО benign FPR** | | **10.0%** | 5.6%→57.5%→10% |

\* ложная_интерпретация: 80% — измерено на rule-based self-check после фикса F;
полный LLM-прогон режима A с фиксом F не переделывался (фикс детерминирован).
Прежний «высокий» recall до фиксов был частично **ложной уверенностью** —
шум извлечения LLM случайно «ловил» галлюцинации, одновременно раздувая FPR до
57.5%. После очистки шума цифры честные.

### 4.2. Режим B — сквозной прод-конвейер на искажениях (37 пар, 1 пациент)

| | critical | benign |
|---|---|---|
| Доля reject | **71.4%** | **0.0%** |

100% reject по антониму/отрицанию/числу/подмене/пропуску; 0% по
интерпретации/галлюцинации/причинности (тонкие типы). **0% ложных reject на
benign** — чистая дискриминация на жёстких типах. (До фикса C режим B давал
вырожденный 100% reject по всему.)

### 4.3. Сквозной тест пациента Ж1 — выбор лучшей из 17 сводок

- **gate: 17/17 pass** (все легитимные сводки прошли).
- **Эталон занял 1-е место** среди 17 кандидатов.
- **0 сбоев JSON** за 15 часов прогона.
- Распределение вердиктов: 5 «Неприемлемо», 12 «Требует редактирования».
- Жёстко отклонены (Неприемлемо + E1): 3 из 8 critical-типов (искажение числа,
  вставка отрицания, пропуск контента) — корректно; **плюс 2 benign ложно**
  (перестановка, нерелевантная вставка).
- 5 critical-типов (интерпретация, антоним, подмена, галлюцинация, причинность)
  получили «Требует редактирования» — ранжированы ниже эталона по баллам
  судей, но не отклонены.

## 5. Почему результаты именно такие

### 5.1. Что объективный слой ловит надёжно — и почему
Надёжно детектируются **искажения проверяемых фактов, которые должны быть
СОХРАНЕНЫ**: числа, единицы, полярность, причинность, интерпретация
(где величина однозначна по единице). Это детерминированные правила без
зависимости от «настроения» LLM — поэтому recall по числам/полярности
стабилен, а benign FPR низкий (10%, и почти весь — мелкий числовой шум, не
сущности). Шум LLM-извлечения сущностей подавлен тремя механизмами фикса E:
self-grounding, cross-text сверка, стем-сопоставление с игнором обрамляющих
слов.

### 5.2. Что объективный слой принципиально НЕ ловит — и почему
Главное ограничение проявилось в тесте пациента: при сверке **сводки с СЫРЫМ
ИСТОЧНИКОМ** объективный слой не может отличить:
- **корректный клинический синтез** («стенокардия напряжения», «артериальная
  гипертензия» — диагнозы, выведенные из описания симптомов в источнике;
  дословно их в источнике НЕТ) от
- **настоящей галлюцинации** (выдуманный факт).

Обе ситуации выглядят одинаково — «сущность есть в сводке, но не в источнике».
Различить их можно только клиническим суждением — это **зона LLM-судей, а не
rule-based слоя**. Поэтому детекцию «лишних сущностей» как жёсткую ошибку
сознательно убрали (иначе эталон ложно получал «галлюцинации»). Аналогично
пропуск отдельного симптома неотличим от закономерной компрессии без знания
«что здесь важно».

### 5.3. Шум и недетерминизм судей 8B — главный лимитирующий фактор
В тесте пациента 8B-судьи:
- жёстко отклонили лишь 3 из 8 critical-типов;
- 5 critical-типов «слили» с эталоном (не отклонили);
- дважды **ложно** отклонили benign (перестановку, нерелевантную вставку);
- дали **недетерминированные** вердикты: на повторном прогоне тех же пар
  3 вердикта перевернулись (антоним и причинность были «Неприемлемо» → стали
  «Требует редактирования»; пропуск — наоборот).

Причина — ограниченная ёмкость 8B-модели: тонкая семантика (подмена отделения,
выдуманный анамнез, ложная интерпретация на неоднозначной единице) требует
клинических знаний и устойчивого рассуждения, которых у 8B недостаточно.
Надёжность ВЫВОДА (валидный JSON) починена полностью; ограничено именно
КАЧЕСТВО суждения.

### 5.4. Почему эталон всё же оказался 1-м
Несмотря на шум, эталон стабильно занимает 1-е место, потому что:
- у него **0 реальных ошибок** объективного слоя (он по определению верен);
- судьи дают ему **наивысший балл** по подкритериям (13 из 15 в тесте) —
  даже шумная 8B-модель в среднем оценивает корректную сводку выше искажённой;
- ранжирование первично по категории судей, затем по числу реальных ошибок,
  затем по баллам судей — компрессия (зашумлённая) в ключ не входит.

### 5.5. Калибровка gate
Прежний `scope=None` ожидал полного покрытия сущностей источника, что для
сжимающей сводки невыполнимо → отклонялось всё, включая эталон. Это была
ошибка калибровки (порог под scope-aware прод-корпус применялся к общим
сводкам). Исправлено: блокируется только катастрофический пропуск критической
категории.

## 6. Ограничения и обоснование апгрейда на DeepSeek-R1 70B

| Упирается в 8B | Что даст 70B (профиль `target`) |
|---|---|
| 5 тонких типов не отклоняются, лишь ранжируются ниже | клиническое суждение → жёсткий reject подмены/галлюцинации/интерпретации |
| Недетерминизм: вердикты перевёртываются между прогонами | устойчивые, воспроизводимые вердикты |
| Ложные E1 на benign (перестановка, вставка) | меньше ложных срабатываний стоп-правила |
| Извлечение сущностей шумит (нужны фиксы E) | чище извлечение → выше честный recall |

Переход — это смена одной строки (`ACTIVE_PROFILE = "target"`), без правок в
коде пайплайна. Объективный слой (rule-based) от модели не зависит и работает
одинаково на любой конфигурации.

## 7. Готовность к продакшену

**Готово:**
- Полный конвейер блоков 0–7, сквозной прогон `run_pipeline.py` (+ `--dry-run`).
- Объективный слой — устойчивый, детерминированный, протестирован.
- Надёжность вывода судей (0 сбоев JSON на длинных прогонах).
- gate, корректно калиброванный под два сценария (общая сводка / scope).
- Детерминированная агрегация со стоп-правилом E1.
- Аудит (JSONL), мониторинг дрейфа, Excel-отчёты.
- Валидационный контур (synthetic) и сквозной тест (eval_patient).
- Чистый репозиторий, документация, self-check'и, `.gitignore` (PHI не для
  публичного репозитория).

**Нужно для прод-качества:**
- Целевая GPU-инфраструктура и профиль `target` (70B) — для надёжной
  дискриминации тонких типов.
- Экспертная разметка → запуск модуля корреляции (`correlation.py`) для
  калибровки и валидации против «золотого стандарта».
- Конкурентный инференс (vLLM-батчинг) — текущий конвейер последовательный;
  для прод-масштаба нужно распараллелить вызовы судей.
