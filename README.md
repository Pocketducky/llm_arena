# Арена LLM — система оценки суммаризаций ЭМК

Техническая документация пайплайна автоматической оценки суммаризаций
электронных медицинских карт (ЭМК), выполненных разными LLM, с помощью
ансамбля LLM-судей + объективного (rule-based) слоя верификации фактов.

Документ описывает: устройство файловой системы проекта, назначение и
устройство каждого файла/модуля, сквозной пайплайн обработки одной пары
«ЭМК → суммаризация», как запускать систему, как управлять моделями
(переключать/добавлять/менять роли↔модели) и куда смотреть за результатами.

> **Связанные документы.** [REPORT.md](REPORT.md) — итоговый отчёт о пилоте:
> подробный разбор хода работы алгоритма, что сделано, какие результаты и
> **почему они такие** (рекомендуется как обзор). [HANDOFF.md](HANDOFF.md) —
> журнал инженерных правок (фиксы A–H) и точка возобновления работы.

> Старая версия системы (`evaluator.py`, монолит с захардкоженными под один
> ЭМК промптами и небезопасной логикой stop-rule) полностью заменена новым
> модульным пайплайном (`config.py` … `run_pipeline.py`) и удалена из рабочего
> дерева; при необходимости доступна в git-истории. Точка входа теперь
> **`run_pipeline.py`**.

## 1. Архитектура пайплайна — общая картина

Раньше (`evaluator.py` v3.1) одна суммаризация прогонялась через 3 модели
по промптам, **захардкоженным под конкретный ЭМК** (КТ ОБП, EMR_01), а
итоговый балл считался по непрозрачной формуле `positive + penalties`, в
которой stop-правило безопасности (E1 — опасная галлюцинация) могло быть
переопределено и не остановить высокую оценку.

Новый пайплайн — это **8 последовательных, независимо тестируемых блоков**
(0–7), каждый — отдельный модуль:

```
ЭМК + Суммаризация
        │
        ▼
[Блок 0]  config.py + ollama_client.py
          — абстрактные роли судей -> модели через профиль; HTTP-клиент Ollama
        │
        ▼
[Блок 1]  preprocessor.py
          — универсальная сегментация документа на канонические разделы
            (жалобы, анамнезы, лаб.данные, инструментальные, диагноз, ...)
        │
        ▼
[Блок 2]  objective_layer.py
          — детерминированное (rule-based) + LLM-сверка фактов:
            числа+единицы, полярность утверждений, ложная причинность,
            ложная интерпретация (vs референсные диапазоны), сущности
            (диагнозы, препараты, процедуры, отделения, симптомы, анамнез)
            -> Precision/Recall/F1
        │
        ▼
[Блок 3]  gate.py  — pre-evaluation gate
          — бинарный фильтр: если критические факты источника вообще
            отсутствуют в кандидате -> «не прошла», дальше LLM не идёт
            (экономия GPU-времени)
        │
        ▼
[Блок 4]  judge.py — LLM-as-Judge, 3 раунда
          • Round 1 — независимая оценка 3 судьями по таксономии A-E
          • Round 2 — cross-peer-review с ПОЛНЫМИ отчётами коллег
          • Round 3 — агрегатор синтезирует версию вердикта + явная
            фиксация всех сигналов E1 (предохранитель безопасности)
        │
        ▼
[Блок 5]  aggregator.py + report.py
          — ДЕТЕРМИНИРОВАННОЕ (не-LLM!) итоговое решение:
            1) проверка stop-rule E1 первым, безусловно
            2) статусы по блокам A-E мажоритарным голосованием судей
            3) итоговая категория — прозрачная таблица решающих правил
          — формирование Excel-отчёта с раздельными осями A-E
        │
        ▼
[Блок 6]  synthetic.py + correlation.py — валидационный контур
          — регрессия на синтетическом stress-датасете управляемых искажений
            (рекол на «опасных» подменах / FP-rate на безобидных правках)
          — расчёт Spearman ρ и F1 с экспертной разметкой (готово к
            заполнению, как только появятся экспертные оценки)
        │
        ▼
[Блок 7]  audit.py + drift.py + run_pipeline.py — аудит, отчётность, дрейф
          — структурированный JSONL audit-лог (вход/выход, версии, решения)
          — снимки распределений + пороговые алерты на дрейф
          — ОРКЕСТРАТОР, связывающий всё воедино: run_pipeline.py
```

Ключевые архитектурные принципы, проведённые через все блоки:

- **Абстракция «роль → модель»** (Блок 0): код пайплайна никогда не
  обращается к конкретным именам LLM — только к ролям `judge_1/2/3`,
  `aggregator`. Что стоит за ролью, определяет `config.py` (раздел 7).
- **Заземление LLM-судей на проверяемых фактах** (Блоки 1–4): судья
  получает не «сырой текст целиком», а структуру разделов + список
  фактов-кандидатов из объективного слоя — он верифицирует, а не
  изобретает оценку с нуля.
- **Детерминированность итогового решения** (Блок 5): окончательную
  категорию и срабатывание предохранителя E1 вычисляет код, а не LLM;
  самооценка LLM-агрегатора сохраняется отдельно (`llm_category`) только
  для сравнения и аудита.
- **«Инфраструктура готова — данные дополнят» (Блоки 6–7)**: модули
  корреляции и дрейф-мониторинга полностью реализованы и самотестируемы
  на синтетических данных уже сейчас; содержательно «оживут», когда
  накопятся экспертная разметка и повторные продуктивные прогоны.

## 3. Модули — что делает каждый файл

### Блок 0 — конфигурация и инфраструктура

#### `config.py`
Единственное место, где задаётся соответствие **«абстрактная роль → конкретная
модель Ollama»**. Остальной код пайплайна никогда не упоминает имена моделей —
только роли `judge_1`, `judge_2`, `judge_3`, `aggregator`.

- `JUDGE_ROLES`, `AGGREGATOR_ROLE`, `ALL_ROLES` — перечень ролей.
- `PROFILES` — словарь именованных профилей: `"pilot"`, `"pilot_diverse"`, `"target"`.
- `ACTIVE_PROFILE = "pilot"` — профиль по умолчанию (см. раздел 7 — как переключать).
- `Profile` (dataclass) и `get_profile(name)` — снимок профиля + удобный доступ
  (`profile.model_for("judge_1")`, `profile.unique_models()`).
- Параметры подключения к Ollama: `OLLAMA_HOST`, `NUM_CTX = 16384` (без явного
  указания Ollama режет контекст до 2048 — обрезая ЭМК!), таймауты, температура.

#### `ollama_client.py`
Переиспользуемый HTTP-клиент для локальных LLM через Ollama — никакой доменной
(медицинской) логики, только инфраструктура:

- `generate()` / `ask_json()` — запрос к модели с автоматическим восстановлением
  JSON из «грязного» ответа.
- `repair_json()`, `extract_json()` — чинят типичные ошибки JSON-вывода LLM
  (лишний текст вокруг, незакрытые скобки, markdown-обёртка ```json ... ```).
- Цепочка повторов при сбое: основной промпт → без `format=json` → упрощённый
  промпт-скелет (унаследовано из `evaluator.py`, проверено практикой).
- `OllamaError` — исключение «модель недоступна / не вернула пригодный JSON».
- `JudgePanel` — связывает роли с моделями через `config.Profile`:
  `panel.ask_json("judge_1", prompt)` сам найдёт нужную модель и сделает запрос;
  `panel.availability_report()` — сверяет, что все модели профиля установлены.

#### `check_environment.py`
Самопроверка окружения **перед запуском**. В отличие от старого `test_setup.py`
(хардкод трёх моделей), читает роли и активный профиль прямо из `config.py` —
поэтому при смене профиля не требует правок.

```bash
python check_environment.py             # проверить активный профиль
python check_environment.py target      # явно проверить другой профиль
```
Проверяет: доступность сервера Ollama, наличие всех моделей профиля,
тестовый round-trip запрос на каждую роль, поддержку `num_ctx`.

### Блок 1 — препроцессор

#### `preprocessor.py`
Делит сырой текст ЭМК (или суммаризации) на **канонические смысловые разделы**:
`COMPLAINTS` (жалобы), `HISTORY_ILLNESS`/`HISTORY_LIFE` (анамнезы), `LABS`,
`INSTRUMENTAL`, `DIAGNOSIS`, `OBJECTIVE_EXAM`, `RECOMMENDATIONS`, `CONCLUSION`, `OTHER`.

Заменяет хрупкий `split_source` из `evaluator.py`, который искал «первый»
маркер из списка, заточенного под один тип карты (КТ ОБП) — и ломался на
любой другой из 26 типов карт в датасете (терапия, онкология, офтальмология…).

Подход: словарь канонических категорий + регулярные выражения-«заголовки»,
собранные по факту встречаемости в реальном датасете; построчный обход с
определением начала нового раздела; резервный режим `_segment_by_inline_labels`
для «нарративных» документов без явных заголовков.

Главные точки входа:
- `segment_emr(text) -> DocumentStructure` — сегментация ЭМК.
- `segment_summary(text) -> DocumentStructure` — сегментация суммаризации
  (с классификацией заголовков по ключевым словам, `_classify_summary_heading`).
- `schema_compliance(summary_structure)` — критерий **D1** таксономии: «наличие
  и корректная последовательность всех пяти разделов промпта».
- `DocumentStructure.text_for(category)`, `.coverage_summary()`,
  `.category_order()` — доступ к результату сегментации.

### Блок 2 — объективный слой

#### `objective_layer.py`
**Детерминированная** (где возможно) фактологическая сверка двух текстов —
без «мнения LLM о тексте». Даёт (а) заземляющие данные для промптов судей
Блока 4 и (б) первый количественный, воспроизводимый сигнал качества.

Пять типов извлекаемых/сравниваемых фактов:

1. **Числовые факты** (`extract_numeric_facts` → `NumericFact`): число +
   единица измерения + подпись показателя + контекст. Rule-based regex —
   именно то, что **целенаправленно искажает** синтетический датасет
   («56 лет»→«46 лет», «40 минут»→«40 часов»).
   Сравнение — `compare_numeric_facts`: находит `NumericMismatch`
   (то же самое значение показателя, другое число) и `UnitMismatch`
   (совпавшее число, другая единица измерения).

2. **Полярность клинических утверждений** (`extract_polarity_facts` →
   `PolarityFact`): предикат + полярность (есть/нет) — под тип искажений
   «инверсия отрицания» («купирован» → «не купирован»). Сравнение —
   `compare_polarity_facts` → `PolarityFlip`.

3. **Семантические сущности** (`extract_semantic_entities`, опционально через
   `JudgePanel`/LLM): диагнозы, препараты, процедуры, отделения, симптомы,
   анамнез жизни —
   `ENTITY_CATEGORIES = (diagnoses, medications, procedures, departments, symptoms, anamnesis)`.
   Сравнение — `compare_entity_sets` → Precision/Recall/F1 по категориям.
   Устойчиво к шуму недетерминированного LLM-извлечения: нечёткое
   сопоставление (`_entity_match` — опечатки/словоформы/расшифровки),
   self-grounding (доверяем сущности, лишь если она реально есть в своём
   тексте) и кросс-сверка с сырым текстом (`_entity_present_in_text`) —
   фантомные «пропуски»/«галлюцинации» извлечения отсеиваются, настоящие
   остаются.

4. **Ложная причинность** (`compare_causality`): введённая в кандидат
   причинная связка («вследствие», «по причине»), которой нет в референсе —
   тип «ложная_причинность», к которому слепы числа/полярность/сущности.

5. **Ложная интерпретация** (`compare_interpretations`): оценочное слово при
   числе, **противоречащее** референсному диапазону («снижено (150/90 мм
   рт. ст.)» — это гипертензия). Отделяет critical «ложную интерпретацию» от
   benign корректной по медицинской верности; диапазоны заданы лишь для
   однозначных по единице величин (АД, ЧСС, гемоглобин, креатинин, явный
   избыток ферментов), неоднозначные — на усмотрение судей.

Главная точка входа — `compare_texts(text_a, text_b, panel=None)` →
`ObjectiveComparisonReport`:
- `.hard_findings()` — человекочитаемый список «жёстких» расхождений.
- `.to_summary()` — компактное JSON-сериализуемое резюме (для audit-лога
  и Excel-отчёта — Блок 7).

### Блок 3 — pre-evaluation gate

#### `gate.py`
Бинарный фильтр **до** привлечения тяжёлых LLM-судей: если суммаризация вообще
не упоминает критические факты источника (диагнозы, ключевые лабораторные
показатели, аллергоанамнез, перенесённые операции), прогон через 3-раундовую
LLM-оценку — трата GPU-времени впустую. Шлюз отсекает такие случаи раньше.

Отличие от Блока 2 по смыслу проверки:
- объективный слой ищет **искажения** (факт упомянут, но неверно);
- шлюз ищет **пропуски** (факт критической категории не встретился вообще).

Решение детерминированное (никаких LLM на этом этапе — быстро) и опционально
усиливается LLM-фильтрацией сущностей (`filter_relevant_entities`), когда
модели доступны.

Главная точка входа — `evaluate_gate(source_text, summary_text, panel=None)` →
`GateDecision` со статусом (`passed`/`needs_revision`/`rejected`) и списком
`GateReason` (для аудита и анализа причин отклонения).

Пороговые константы (видны в audit-логе как структурный снимок версий):
`CRITICAL_NUMERIC_CATEGORIES`, `CRITICAL_PREDICATES`, `MIN_SCHEMA_SECTIONS`,
`MIN_ENTITY_RECALL`.

### Блок 4 — LLM-as-Judge

#### `judge.py`
Самый объёмный модуль (~1000 строк). Полностью заменяет старые промпты
`PROMPT_CLINICAL`/`PROMPT_INSTRUMENTAL`/`PROMPT_PENALTIES` (`evaluator.py`),
захардкоженные под один ЭМК — новые промпты **общие** и заполняются
структурой конкретной пары из Блоков 1–3 («заземление на проверяемых фактах»).

Таксономия оценки — блоки **A–E** (дословно из дизайна исследования, раздел 4.1):
- **A** — точность, **B** — полнота, **C** — релевантность,
  **D** — структура (опирается на `schema_compliance`, Блок 1),
  **E** — безопасность (содержит критический подкритерий **E1** —
  «опасная галлюцинация» = предохранитель, переопределяющий всё).

Структурированный JSON-вывод: бинарные подкритерии (A1…E3) + краткое
обоснование — вместо произвольных баллов «0–15 на глаз».

Трёхраундовая схема:
1. **Round 1** (`score_round1`) — независимая оценка тремя судьями
   (`JUDGE_ROLES` из `config.py`), блок за блоком (`score_block`).
2. **Round 2** (`score_round2`) — cross-peer-review: каждый судья получает
   **полные** отчёты коллег (`_format_full_report`, без обрезки — в отличие
   от старого `compact()`, резавшего списки галлюцинаций) и пересматривает
   свою оценку с учётом их аргументов.
3. **Round 3** (`score_round3`) — агрегатор синтезирует свою версию вердикта
   и явно проверяет E1; `_collect_e1_signals` прозрачно собирает сигналы из
   ВСЕХ источников (R1, R2, R3) для последующей детерминированной проверки.

Сохранены доказавшие себя инженерные решения из старого кода (теперь —
в обобщённом виде в `ollama_client.py`): repair JSON, retry-цепочка,
перемешивание порядка судей (борьба с position bias), чекпоинты на диск
(`load_checkpoint`/`save_checkpoint`, каталог `checkpoints/judge/`).

Версионирование (для audit-лога, Блок 7): `PROMPT_SET_VERSION = "judge-prompts-v1"`,
`TAXONOMY_VERSION = "design_doc-4.1-v1"`.

Главная точка входа — `evaluate_summary(source_text, summary_text, emr_id,
model_id, panel=None) -> dict`. Возвращает словарь со всеми промежуточными
данными (`gate`, `objective`, `e1_signals`, `r1`, `r2`, `r3`) — независимо
от того, прошла пара весь путь или была отклонена шлюзом/упала с ошибкой
(`_err`) — поле `"objective"` присутствует ВСЕГДА (либо реальное резюме,
либо `None` с явным пояснением, почему его нет).

### Блок 5 — детерминированная агрегация и отчётность

#### `aggregator.py`
Полностью заменяет старую формулу `final_score = positive + penalties` и
логику «у кого балл не ноль, тот и арбитр». **LLM здесь больше ничего не
решает** — единственный источник итоговой категории — этот прозрачный,
воспроизводимый код поверх структурированных данных Блоков 1–4.

Порядок решения (`_decide`):
1. **Стоп-правило E1 — первым и безусловно.** Если флаг подняли судьи (R1
   или уточнённый R2) или сам агрегатор (R3) — категория «Неприемлемо»
   фиксируется немедленно; шаги 2–3 это решение не пересматривают.
2. Раздельный статус/балл по каждому блоку **A–E** — мажоритарное
   голосование судей по их **финальной** позиции (`_final_reports`:
   R2-отчёт, если состоялся, иначе R1).
3. Итоговая категория — таблица решающих правил поверх (1)–(2) + решения
   шлюза.

Самооценка LLM-агрегатора (Round 3) сохраняется отдельно как `llm_category`/
`llm_verdict` — НЕ для итогового решения, а для аудита/сравнения «насколько
часто и в чём код расходится с самооценкой модели» (метрика для Блоков 6–7).

`DECISION_TABLE_VERSION = "aggregator-decision-table-v1"` — версия таблицы
решающих правил (для audit-лога).

Главная точка входа — `finalize(evaluation: dict) -> dict`: принимает сырой
результат `judge.evaluate_summary`, возвращает финализированный словарь с
полями `category`, `verdict`, `blocks` (статусы A–E), `e1_triggered`,
`e1_sources`, `llm_category`, `decision_path`, плюс всё, что было в `evaluation`
(включая `objective` — Блок 2, `gate` — Блок 3).

#### `report.py`
Формирование итогового **Excel-отчёта** (4 листа) под новую модель данных
(раздельные оси A–E + детерминированная категория из `aggregator.py`,
вместо старого единого `final_score`):

| Лист | Содержимое |
|---|---|
| **Сводная таблица** | По каждой паре: итоговая категория (код, не самооценка LLM), флаг E1 + источники, решение шлюза, **«Объективный слой» — числовые/полярные расхождения и F1 по сущностям рядом с LLM-оценкой**, статус каждого блока A–E, категория по версии LLM-агрегатора (для сравнения), полный вердикт |
| **Детали по блокам** | По каждой паре/судье/блоку — какие именно подкритерии НЕ прошли мажоритарную проверку, с конкретными обоснованиями судей |
| **Статистика** | По моделям: распределение по 3 категориям, частота E1, решения шлюза, согласие код↔LLM, **средняя доля пар с числовыми/полярными расхождениями объективного слоя** |
| **🚨 Критические** | Все срабатывания E1 (с источниками и примерами) + все блоки со статусом «issues» |

Главная точка входа — `save_results(results: list[dict], path) -> None`,
принимает список результатов, уже прошедших `aggregator.finalize()`.

### Блок 6 — валидационный контур

#### `synthetic.py`
Регрессионное тестирование на **синтетическом stress-датасете управляемых
искажений** (`materials/Синтетический_НД_..._Сеченовский_университет.xlsx`):
10 клинических случаев (колонки-пациенты), в каждом — строка 0 исходный
нарратив ЭМК, строка 1 эталонная суммаризация, строки 2–38 та же суммаризация
с **внедрёнными искажениями**. Ключевое свойство: тип искажения в строке N
одинаков для всех 10 пациентов → **ground truth = номер строки**, а не
результат diff-инференса.

- `ROW_DISTORTIONS: dict[int, DistortionSpec]` — **единый редактируемый
  источник правды** (легенда): тип, критичность (`CRITICAL`/`BENIGN`), блок
  таксономии и пример правки для каждой строки. Пограничные строки помечены
  дефолтами — переразметка = правка одной записи здесь.
- `load_dataset()` → `list[CaseColumn]` (source / gold / candidates) и
  `build_pairs(cases, reference=...)` — пары «референс → искажённый кандидат».
- `check_legend_consistency()` — guard: предупреждает, если файл «поехал» и
  строки больше не соответствуют легенде (не падает — поднимает флаг).

Два режима оценки (CLI `--mode a|b|both`):
- **Режим A — детекция** (`run_detection` → `summarize_detection`): сравнивает
  эталон (стр.1) с каждым искажением через объективный слой Блока 2 (rule-based
  + опционально LLM-сущности). Метрики по типам: **recall** на critical
  (обязаны ловиться) и **FPR** на benign (не должны). Сигналы: числа, единицы,
  полярность, сущности, причинность, интерпретация. Быстрый, изолирует ровно
  внедрённое искажение.
- **Режим B — сквозной прод-прогон** (`run_production` → `summarize_production`):
  гоняет пару эталон→искажение через полный конвейер `judge.evaluate_summary`
  (шлюз + 3 судьи + агрегатор + E1) и смотрит вердикт accept/reject. Тест
  дискриминирующей способности всего стека; медленный (full pipeline на пару).

Флаги: `--limit-cols N` (ограничить число пациентов), `--no-llm` (режим A
только rule-based), `--profile`, `--xlsx`, `--excel-out reports/*.xlsx`,
`--ref-metrics` (доп. reference-метрики, см. `reference_metrics.py`),
`--self-check` (дымовой прогон легенды + классификатора + rule-based детекции).

#### `reference_metrics.py`
Reference-based метрики качества из дизайна (Раздел 4.2), применяются **только
там, где есть эталонный текст суммаризации** — на синтетике это эталон (стр.1),
сравниваемый с кандидатом. В продуктивном пути (исходник ЭМК → суммаризация)
эталона-суммаризации нет, поэтому модуль там не используется.
- `rouge_l(reference, candidate)` — ROUGE-L (лексическое перекрытие) через LCS
  токенов; без внешних зависимостей.
- `bertscore(references, candidates)` — BERTScore (семантическое сходство) через
  пакет `bert-score` (ленивый импорт; тянет torch+transformers — опциональная
  установка `pip install -r requirements-metrics.txt`; модель по умолчанию —
  многоязычный `bert-base-multilingual-cased`).
Подключены в `synthetic.py` под флагом `--ref-metrics` (режим A): средние
ROUGE-L/BERTScore F1 по каждому типу искажения, в консоль и Excel. Метрики
КОАРСНЫЕ относительно одиночных искажений (точечная замена слабо двигает балл) —
служат общим индикатором близости к эталону, тонкую детекцию даёт объективный
слой + судьи.

#### `correlation.py`
Расчёт **корреляции авто-оценки пайплайна с экспертной разметкой**
(Spearman ρ + F1 бинарной классификации «приемлемо/неприемлемо»). На момент
написания (2026-06) экспертная разметка ещё не получена — модуль полностью
готов к использованию (`_self_check` тестирует на заглушках), сценарий:

```python
experts = correlation.load_expert_annotations("materials/экспертная_разметка.xlsx")
autos   = [correlation.AutoRecord.from_evaluation(case_id, finalize(...)) for ...]
report  = correlation.correlate(autos, experts)
print(report.render())
```

`to_binary(category)` — бинаризация по плану Блока 6 («Готово к применению»
→ приемлемо; «Требует редактирования»/«Неприемлемо» → неприемлемо).
Использует `scipy.stats.spearmanr` (даёт ρ + p-value).

### Блок 7 — аудит, отчётность, дрейф, оркестрация

#### `audit.py`
Структурированный **audit-лог в формате JSONL** — «вход/выход каждого модуля,
версии промптов/моделей/порогов, решения и их обоснования» (план, Блок 7).

- Формат JSONL: одна запись на строку — устойчив к обрыву посередине
  прогона, грепается, читается потоково.
- В лог попадают **sha256-хэши** текстов ЭМК/суммаризации, а НЕ сам текст —
  доказательство «эта пара была оценена именно так» без хранения
  персональных медицинских данных в логах на диске.
- «Версии» — структурный снимок (`versions_snapshot`): активный профиль
  моделей, `judge.PROMPT_SET_VERSION`, `judge.TAXONOMY_VERSION`,
  `aggregator.DECISION_TABLE_VERSION` и фактические ЗНАЧЕНИЯ порогов
  `gate.MIN_*`/`gate.CRITICAL_*` — не абстрактный номер сборки, а буквально
  «чем именно было оценено» (для прямого сравнения двух прогонов и честной
  регуляторной реконструкции решений).

Точки входа:
- `AuditLogger(run_id=...)` — аппендер, один файл на прогон
  (`audit_log/{run_id}.jsonl`); `.log_evaluation(...)` — собрать запись из
  результата `aggregator.finalize` и сразу дописать.
- `load_entries(path)` — прочитать JSONL обратно (вход для `drift.py`).

#### `drift.py`
**Скелет мониторинга дрейфа**: «сохранение распределений баллов по времени +
пороговые алерты» (план, Блок 7). Это инфраструктура — построена и
самопротестирована на синтетических снимках; реальные алерты появятся,
когда накопится 2+ сопоставимых прогонов одного профиля.

- `compute_snapshot(entries) -> DriftSnapshot` — строит снимок прямо из
  записей audit-лога: распределение итоговых категорий, статусов шлюза,
  средние объективные метрики (доля числовых/полярных расхождений,
  средний F1 по сущностям), разбивка по моделям. Сохраняется в
  `audit_log/drift_snapshots/{run_id}.snapshot.json`.
- `compare_snapshots(baseline, current) -> list[DriftAlert]` — сравнивает
  два снимка ОДНОГО профиля; поднимает алерт, если изменение превышает
  порог (`DEFAULT_THRESHOLDS`: рост доли «Неприемлемо» >10%, доли отклонений
  шлюза >10%, суммарный сдвиг распределения категорий >15% — первое
  приближение, калибруется на реальных повторных прогонах).
- Алерт **не диагностирует причину** дрейфа (промпты/модели/данные/баг) —
  это решает человек; алерт лишь указывает «здесь что-то изменилось».

#### `run_pipeline.py` ⭐ ГЛАВНАЯ ТОЧКА ВХОДА
**Оркестратор**, связывающий все блоки 0–7 в один end-to-end прогон:

```
загрузка пар (data/summaries.xlsx)
        │
        ▼
judge.evaluate_summary    — Блоки 1-4 (препроцессор, объективный слой,
        │                    шлюз, LLM-as-Judge); чекпоинты на диск
        ▼
aggregator.finalize       — Блок 5 (детерминированное решение)
        │
        ├──▶ audit.AuditLogger.log_evaluation   — Блок 7 (JSONL audit-лог)
        │
        ▼ (после всех пар)
report.save_results       — Блок 5/7 (итоговый Excel)
        ▼
drift.compute_snapshot    — Блок 7 (снимок для мониторинга дрейфа)
```

Главная функция — `run(limit=None, profile=None, run_id=None,
use_checkpoints=True) -> dict`. Содержит **обработку отказов на уровне
пары**: если `judge.evaluate_summary` упало с исключением (например,
`OllamaError` — модель не вернула валидный JSON), пара превращается в
результат `"ошибка"`/«Неприемлемо» через `judge._err(...)`, ошибка
логируется, и прогон продолжается со следующей парой — единичный сбой не
обрушивает многочасовой батч на 156 пар (см. раздел 9).

CLI-флаги: `--limit N` (демо-прогон на N первых парах), `--profile`,
`--run-id`, `--no-checkpoints`, `--dry-run` (прогон проводки на
заглушках, без единого обращения к LLM — проверяет, что весь конвейер
`judge → aggregator → audit → report → drift` собран правильно).

## 4. Сквозной путь одной пары через пайплайн

Что происходит с одной парой (ЭМК, суммаризация одной из 6 моделей) внутри
`run_pipeline.run()`:

1. **Загрузка**: строка `(emr_id, model_id, source_text, summary_text)` из
   `data/summaries.xlsx`.
2. **Чекпоинт**: если есть сохранённый результат для этой пары
   (`checkpoints/judge/{emr_id}__{model_id}.json`) и он в новом формате —
   используется он (экономия времени при повторных запусках/доработке).
3. **`judge.evaluate_summary(source, summary, emr_id, model_id, panel)`**:
   a. `preprocessor.segment_emr/segment_summary` — структура разделов (Блок 1);
   b. `objective_layer.compare_texts` — фактологическая сверка, отчёт + резюме (Блок 2);
   c. `gate.evaluate_gate` — решение «прошла/не прошла» (Блок 3);
      — если шлюз отклонил: дальше LLM-судьи НЕ вызываются (экономия GPU);
   d. при прохождении шлюза — **3 раунда LLM-as-Judge** (Блок 4):
      Round 1 (3 судьи независимо по A-E) → Round 2 (cross-peer-review с
      полными отчётами) → Round 3 (агрегатор + сбор всех сигналов E1);
   e. возвращается единый словарь со всеми промежуточными данными.
4. **`aggregator.finalize(evaluation)`** — детерминированное решение (Блок 5):
   проверка E1 → статусы блоков A-E мажоритарным голосованием → итоговая
   категория по таблице решающих правил.
5. **`audit.AuditLogger.log_evaluation(...)`** — запись в JSONL audit-лог:
   хэши текстов, версии промптов/таксономии/решающей таблицы/порогов,
   решения и обоснования (Блок 7).
6. Сохранение чекпоинта (`judge.save_checkpoint`).
7. **После всех пар**: `report.save_results` (Excel-отчёт) и
   `drift.compute_snapshot` (снимок распределений для мониторинга дрейфа).

Если на любом из шагов 3–4 произойдёт необработанное исключение (например,
LLM не вернула валидный JSON после всех попыток восстановления) —
`run_pipeline` перехватывает его, превращает пару в «ошибка»/«Неприемлемо»
через `judge._err(...)`, логирует и продолжает со следующей парой.

## 5. Установка и подготовка окружения

### 5.1. Системные требования
- Python 3.10+ (используется `from __future__ import annotations`, dataclasses, type hints с `|`).
- [Ollama](https://ollama.com) — локальный сервер для запуска LLM (`ollama serve`, порт `11434`).
- Достаточно RAM/VRAM под модели активного профиля (см. раздел 7).

### 5.2. Python-зависимости
```bash
pip install requests pandas openpyxl scipy chardet
```
- `requests` — HTTP-вызовы к Ollama (`ollama_client.py`);
- `pandas`, `openpyxl` — чтение/запись Excel (`prepare_data.py`, `report.py`, `correlation.py`);
- `scipy` — `scipy.stats.spearmanr` для расчёта корреляции (`correlation.py`);
- `chardet` — определение кодировки исходных `.txt` файлов (`prepare_data.py`).

> Если каких-то библиотек не хватает — `pip install <имя>`. Стандартная
> библиотека (`json`, `hashlib`, `dataclasses`, `argparse`, `logging`, ...)
> используется без дополнительной установки.

### 5.3. Запуск сервера Ollama
```bash
ollama serve
```
Оставьте терминал открытым (или запустите как фоновую службу). Проверка:
```bash
curl http://localhost:11434/api/tags
```

### 5.4. Загрузка моделей
Перед запуском убедитесь, что в Ollama установлены ВСЕ модели,
перечисленные в активном профиле `config.py` (по умолчанию — `"pilot"`,
содержит только `qwen3:8b`):
```bash
ollama pull qwen3:8b
ollama list           # проверить, что модель скачана
```
Какие модели нужны для других профилей — см. раздел 7.

### 5.5. Подготовка датасета
Если `data/summaries.xlsx` ещё не создан (или нужно обновить из новых
исходных файлов в `raw_data/`):
```bash
python prepare_data.py
```
Соберёт `data/summaries.xlsx` из `raw_data/text{N}_source.txt` +
`text{N}_model{1..6}.txt` (ожидается 26 ЭМК × 6 моделей = 156 строк).

### 5.6. Самопроверка окружения
```bash
python check_environment.py
```
Проверит: доступность сервера Ollama, что все модели активного профиля
установлены, тестовый запрос на каждую роль, поддержку `num_ctx=16384`
(критично — без него Ollama режет контекст до 2048 символов и обрезает ЭМК).

## 6. Как запускать

Главная точка входа — **`run_pipeline.py`**.

### 6.1. Проверка проводки без обращения к LLM (рекомендуется первым делом)
```bash
python run_pipeline.py --dry-run
```
Прогоняет 3 заглушки через весь конвейер `judge → aggregator → audit →
report → drift` — без единого вызова Ollama. Подтверждает, что весь монтаж
собран правильно, за секунды.

### 6.2. Демонстрационный прогон на нескольких парах
```bash
python run_pipeline.py --limit 2
```
Прогоняет первые N пар на реальных LLM (живые вызовы к Ollama). Полезно,
чтобы убедиться, что пайплайн работает на живых данных, прежде чем
запускать полный прогон. **Внимание**: на пилотном железе (один `qwen3:8b`
на все роли, без параллелизма GPU, режим «размышления» при 16K контексте)
одна пара — это 20+ обращений к модели и может занимать **несколько минут
на запрос / десятки минут на пару**.

### 6.3. Полный прогон (все 156 пар = 26 ЭМК × 6 моделей)
```bash
python run_pipeline.py
```
Это **многочасовая задача** на пилотном железе (по факту — порядка
8–9 минут на пару в демо-прогоне → ориентировочно ~20+ часов на 156 пар).
Рекомендуется запускать ночью / на выделенном железе / в фоне:

```bash
# Пример фонового запуска (Linux/macOS):
nohup python run_pipeline.py > full_run.log 2>&1 &
echo "PID: $!"
tail -f full_run.log              # следить за прогрессом
```

```powershell
# Пример фонового запуска (Windows PowerShell):
Start-Process python -ArgumentList "run_pipeline.py" `
  -RedirectStandardOutput full_run.log -RedirectStandardError full_run.err -NoNewWindow
```

Прогон **возобновляем**: чекпоинты (`checkpoints/judge/`) сохраняются по
каждой паре сразу после оценки — при перезапуске уже оценённые пары не
считаются заново (если не передан `--no-checkpoints`).

### 6.4. Полезные флаги
| Флаг | Назначение |
|---|---|
| `--limit N` | оценить только первые N пар (демонстрация/отладка) |
| `--profile NAME` | использовать другой профиль моделей вместо `config.ACTIVE_PROFILE` (см. раздел 7) |
| `--run-id ID` | задать свой идентификатор прогона (по умолчанию — метка времени `run-YYYYMMDDTHHMMSSZ`); определяет имена файлов audit-лога/отчёта/снимка |
| `--no-checkpoints` | игнорировать сохранённые чекпоинты, оценить заново |
| `--dry-run` | сухой прогон проводки на заглушках, без LLM (см. 6.1) |

### 6.5. Полезные вспомогательные команды
```bash
python check_environment.py          # проверка окружения перед запуском
python check_environment.py target   # проверка конкретного профиля
python prepare_data.py               # (пере-)сборка датасета из raw_data/
```

## 7. Как управлять моделями (роли ↔ модели, профили)

Это самая важная часть для повседневного использования: **весь пайплайн
работает с абстрактными ролями, а не с именами моделей**. Поменять модели —
значит отредактировать только `config.py`, без единой правки в остальном коде.

### 7.1. Роли
Их ровно четыре, и их назначение фиксировано:
- `judge_1`, `judge_2`, `judge_3` — три независимых судьи (Round 1), затем
  участники cross-peer-review (Round 2);
- `aggregator` — финальный синтезатор вердикта (Round 3) + явная проверка E1.

### 7.2. Профили — готовые наборы «роль → модель»
В `config.py` определены три профиля (словарь `PROFILES`):

| Профиль | Состав | Когда использовать |
|---|---|---|
| `"pilot"` (используется по умолчанию) | все 4 роли → `qwen3:8b` | то, что реально установлено локально прямо сейчас; полностью рабочий, но без диверсификации точек зрения между судьями |
| `"pilot_diverse"` | `judge_1`→`qwen3:8b`, `judge_2`→`llama3.1:8b`, `judge_3`→`mistral:7b`, `aggregator`→`qwen3:8b` | после того как подтянете доп. лёгкие модели — разные архитектуры снижают корреляцию ошибок судей, усиливая смысл cross-peer-review |
| `"target"` | все 3 судьи → `deepseek-r1:70b`, `aggregator` → `qwen3-next:80b` | целевая (production) конфигурация по дизайну исследования — на GPU-инфраструктуре (2×H100 80GB) |

### 7.3. Как переключить профиль

**Способ 1 — на лету, через CLI-флаг (ничего не редактируя в коде):**
```bash
python run_pipeline.py --profile pilot_diverse
python run_pipeline.py --profile target
python check_environment.py target
```

**Способ 2 — поменять профиль по умолчанию:**
Откройте `config.py`, найдите строку:
```python
ACTIVE_PROFILE = "pilot"
```
и замените на нужное имя (`"pilot_diverse"` или `"target"`).

### 7.4. Как добавить/скачать новую модель
```bash
ollama pull llama3.1:8b
ollama pull mistral:7b
ollama list                    # убедиться, что модель появилась
python check_environment.py    # проверить, что всё доступно и отвечает
```

### 7.5. Как создать СВОЙ профиль / изменить распределение ролей
Откройте `config.py`, добавьте новый словарь по образцу существующих:
```python
MY_CUSTOM_PROFILE: dict[str, str] = {
    "judge_1":    "qwen2.5:14b",
    "judge_2":    "llama3.1:8b",
    "judge_3":    "mistral:7b",
    "aggregator": "qwen2.5:14b",
}
```
и зарегистрируйте его в словаре `PROFILES`:
```python
PROFILES: dict[str, dict[str, str]] = {
    "pilot":         PILOT_PROFILE,
    "pilot_diverse": PILOT_PROFILE_DIVERSE,
    "target":        TARGET_PROFILE,
    "my_custom":     MY_CUSTOM_PROFILE,     # ← новая строка
}
```
Дальше — `python run_pipeline.py --profile my_custom`. **Никаких других
правок в коде пайплайна не требуется** — это и есть смысл архитектуры
«роль → модель» из Блока 0.

> Важно: каждой роли должна соответствовать модель, которая РЕАЛЬНО
> установлена в Ollama (`ollama list`). Несоответствие будет обнаружено
> сразу при `check_environment.py` или при первом обращении (`OllamaError`).

### 7.6. Параметры подключения к моделям
В `config.py` также настраиваются (обычно трогать не нужно, но при смене
очень больших моделей — может понадобиться):
- `NUM_CTX = 16384` — размер контекстного окна (КРИТИЧНО: меньшие значения
  обрежут длинные ЭМК);
- `TIMEOUT_SECONDS = 300` — таймаут одного запроса;
- `DEFAULT_TEMPERATURE = 0.1` — низкая температура для воспроизводимости
  оценок;
- `REQUEST_PAUSE_SECONDS = 2` — пауза между последовательными запросами
  (щадит GPU/CPU при долгих батчах).

## 8. Где смотреть результаты

После завершения прогона (`run_pipeline.run`, обычного или `--limit`)
сообщаются три пути (видны и в логе, и в возвращаемом словаре):

| Артефакт | Расположение | Что внутри |
|---|---|---|
| **Audit-лог** | `audit_log/{run_id}.jsonl` | по одной JSON-записи на пару: хэши текстов, версии промптов/таксономии/порогов, решения шлюза/судей/агрегатора и их обоснования — см. `audit.py` |
| **Excel-отчёт** | `reports/{run_id}.xlsx` | 4 листа: «Сводная таблица», «Детали по блокам», «Статистика», «🚨 Критические» — см. описание `report.py` в разделе 3 |
| **Снимок дрейфа** | `audit_log/drift_snapshots/{run_id}.snapshot.json` | распределения категорий/решений шлюза/объективных метрик для этого прогона — вход для `drift.compare_snapshots` при появлении следующего сопоставимого прогона |
| **Чекпоинты** | `checkpoints/judge/{emr_id}__{model_id}.json` | сырые результаты `judge.evaluate_summary` по каждой паре — переиспользуются при повторных запусках |

### Как сравнить два прогона на дрейф
```python
import drift
baseline = drift.snapshot_from_audit_log("audit_log/run-A.jsonl")
current  = drift.snapshot_from_audit_log("audit_log/run-B.jsonl")
alerts = drift.compare_snapshots(baseline, current)
print(drift.render_alerts(alerts, baseline=baseline, current=current))
```

### Как прочитать audit-лог вручную
```python
import audit
entries = audit.load_entries("audit_log/block7-e2e-demo2.jsonl")
for e in entries:
    print(e["emr_id"], e["model_id"], "->", e["category"])
    print("  объективный слой:", e["objective"])
    print("  версии:", e["versions"]["prompt_set_version"], e["versions"]["thresholds"])
```

## 9. Известные ограничения и решённые проблемы

### 9.1. Надёжность JSON-вывода `qwen3:8b` (известная проблема пилотного железа)
В демонстрационном прогоне на реальных LLM (`run_id=block7-e2e-demo2`)
модель `qwen3:8b` дважды не смогла вернуть валидный JSON на этапе
извлечения сущностей в шлюзе (`gate.evaluate_gate` → `extract_semantic_entities`)
даже после внутренней цепочки повторов в `ollama_client.ask_json`
(`OllamaError: модель не вернула пригодный JSON после 2 попыток`).

Это — известная особенность лёгких локальных моделей в режиме
«размышления» (thinking mode) на длинном контексте: скрытые
`<think>`-рассуждения съедают бюджет `num_predict` ДО структурированного
ответа, и большой JSON (особенно полный отчёт A–E в R2) обрывается.

**Корневое решение (фикс G, реализовано в `judge.py`/`ollama_client.py`):**
- `think=False` во всех раундах судей (R1/R2/R3) — весь бюджет идёт на JSON,
  а не на скрытые рассуждения (тот же приём уже применялся для извлечения
  сущностей);
- толерантный мердж R2 (`judge._merge_full_report`) — ответ модели
  накладывается на валидный отчёт R1; обрыв/пропуск поля больше не фатален,
  R2 **никогда не падает** (худший случай = отчёт R1 без изменений);
- увеличен `num_predict` для крупных выводов R2/R3.

Проверено: на полном ночном прогоне (17 сводок, ~15 ч) — **0 сбоев JSON**.

**Защита в глубину (сохранена):** в `run_pipeline.run` каждая пара по-прежнему
обёрнута в `try/except` (исключение → результат `"ошибка"`, прогон
продолжается) — на случай любых иных сбоев, не давая единичному сбою обрушить
многочасовой батч.

### 9.2. Скорость полного прогона на пилотном железе
Один `qwen3:8b` без параллелизма GPU делает ~20+ обращений к модели на одну
пару (gate: извлечение сущностей; Round 1: 3 судьи × 5 блоков = 15 вызовов;
Round 2: ~3; Round 3: 1). Замеренное время — ~8–9 минут/пара ⇒ полный прогон
156 пар — это многочасовая (порядка суток) задача. `run_pipeline.py`
полностью её поддерживает без изменений кода — рекомендуется запуск ночью
или на выделенном железе (см. раздел 6.3). На целевом профиле (`"target"`,
GPU-инфраструктура 2×H100) ожидается значительное ускорение.

### 9.3. Профиль `"pilot"` использует одну модель на все роли
Это снижает «разнообразие точек зрения» между судьями (одна и та же модель,
оценивающая сама себя трижды, скорее согласится сама с собой, чем три
независимые архитектуры). Решение готово — `"pilot_diverse"` (раздел 7) —
активируется после того, как будут подтянуты `llama3.1:8b` и `mistral:7b`.

### 9.4. Корреляция с экспертной разметкой и калибровка алертов дрейфа
`correlation.py` и пороги в `drift.DEFAULT_THRESHOLDS` — полностью готовая
инфраструктура, но содержательно «оживут» только когда появятся (а)
экспертная разметка хотя бы на части датасета и (б) 2+ сопоставимых
продуктивных прогона одного профиля. До этого момента оба модуля
протестированы на синтетических заглушках (`_self_check`).

### 9.5. Калибровка gate под сжимающие сводки (фикс H)
При `scope=None` gate ожидал полного покрытия сущностей источника, что для
сжимающей сводки невыполнимо → отклонялись ВСЕ сводки, включая эталон. Сделан
scope-aware (`gate._entity_recall_reasons`): при `scope=None` блокируется только
полное отсутствие критической категории (диагнозы/препараты, `CRITICAL_ENTITY_CATEGORIES`),
низкое покрытие прочего — закономерная компрессия (полноту оценивают судьи).
Проверено: эталон → pass, вырожденная сводка → reject.

### 9.6. Предел дискриминации на 8B — обоснование апгрейда на 70B
Надёжность ВЫВОДА судей починена (фикс G, 0 сбоев JSON), но КАЧЕСТВО суждений
8B ограничено: в сквозном тесте пациента 8B-судьи жёстко отклонили лишь 3 из 8
типов критических искажений, 5 «слили» с эталоном, дважды ложно отклонили
benign, и давали **недетерминированные** вердикты (3 перевернулись между
прогонами). Эталон при этом стабильно занимает 1-е место. Подробный разбор
причин и метрики — в [REPORT.md](REPORT.md), разделы 4–6. Решение —
профиль `target` (DeepSeek-R1 70B), смена одной строки в `config.py`.

## 10. Глоссарий терминов проекта

| Термин | Значение |
|---|---|
| **ЭМК** | Электронная медицинская карта — исходный документ, который суммаризируют LLM |
| **Роль** | Абстрактное имя участника оценки (`judge_1/2/3`, `aggregator`), не привязанное к конкретной модели |
| **Профиль** | Именованный набор соответствий «роль → модель» (`pilot`, `pilot_diverse`, `target`) |
| **Таксономия A–E** | Пять осей оценки качества суммаризации: точность (A), полнота (B), релевантность (C), структура (D), безопасность (E) — из дизайна исследования, раздел 4.1 |
| **E1** | Критический подкритерий блока E («опасная галлюцинация») — предохранитель: его срабатывание у ЛЮБОГО источника немедленно и безусловно даёт категорию «Неприемлемо» |
| **Объективный слой** | Детерминированная (rule-based + опционально LLM) фактологическая сверка — числа, полярность утверждений, сущности — независимая от «мнения» LLM-судей (Блок 2) |
| **Шлюз (gate)** | Бинарный фильтр перед LLM-as-Judge: отсекает суммаризации без критических фактов источника, экономя GPU-время (Блок 3) |
| **Раунд 1/2/3** | Этапы LLM-as-Judge: независимая оценка → cross-peer-review с полными отчётами → синтез агрегатором (Блок 4) |
| **Заземление (grounding)** | Передача судье конкретных фактов-кандидатов из объективного слоя/препроцессора вместо «сырого текста целиком» — судья верифицирует, а не изобретает |
| **Чекпоинт** | Сохранённый на диск результат оценки одной пары — позволяет прерывать/возобновлять многочасовые прогоны без потери прогресса |
| **Audit-лог** | Структурированный JSONL-журнал входов/выходов/решений/версий каждого прогона — для воспроизводимости и регуляторной отчётности (Блок 7) |
| **Снимок дрейфа** | Зафиксированное распределение категорий/метрик одного прогона — единица сравнения для мониторинга дрейфа (Блок 7) |
| **Дрейф** | Значимое изменение распределений между двумя сопоставимыми прогонами одного профиля — сигнал «здесь что-то изменилось», требующий разбора человеком |
| **`run_id`** | Идентификатор одного прогона — связывает audit-лог, отчёт и снимок дрейфа (по умолчанию — метка времени) |
